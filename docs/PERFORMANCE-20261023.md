## 2. 已复现的卡顿放大机制

源码：`src/lib/renderQuality.ts:20`、`src/components/Stage.tsx:166`、`src/components/MoonCanvas.tsx:240`。

当前门限是 `now - lastPaint < interval - 0.5`（月球同理），绘制后直接把 `lastPaint` 设为当前时间。错过理想绘制时刻后，剩余时间被丢弃；绘制频率只能落在输入回调周期的整数倍上。它不会自动维持目标平均频率。

下面是 **20 秒合成时间序列重放**，统计后段绘制频率；输入回调序列是人为指定的，并非该电脑的屏幕刷新率或实测回调：

| 输入回调 Hz | 当前正常档，目标 30Hz | 当前降级档，目标 20Hz | 保留时间余量的候选调度，目标 30Hz |
| ---: | ---: | ---: | ---: |
| 60 | 30 | 20 | 30 |
| 75 | 25 | 18.75 | 30 |
| 144 | 28.8 | 18 | 30 |
| 30 | 30 | **15** | 30 |
| 30.5 | **15.25** | **15.25** | 约 30 |
| 24 | 24 | **12** | 24 |

直接导入当前 RenderBudget、结合当前门限的重放：稳定输入 24Hz、自身绘制成本始终为 0，在预热期后再采样约 2.5 秒进入 limited，随后稳定绘制 **12 次/秒**。另一个反例是 30.5Hz：即使预算不降级，当前正常档也只绘制 15.25 次/秒。

这些反例证明当前代码能放大卡顿，与用户目测约 15fps 相容；**不能据此断言用户实际输入回调是 30.5Hz，或真实根因已被完全定位**。月球 dirty / 拖拽和星空 dirty 会绕过部分限帧，表格针对静置、正常动态、可见、无 dirty 的状态；正好对应此次新增反馈所应优先检查的状态。

RenderBudget 的额外问题：

- `gap` 来自每次 rAF 回调，不是画布自己的绘制间隔。CSS 合成压力、别的 JS、浏览器调度或诊断开销造成的慢回调都可能让两个画布一起降级，无法据此归因到画布。
- 直接导入重放中，20% 回调间隔 50ms，其余 16.67ms，自身成本 0，也会进入 limited。随后输入 3600 个稳定 60Hz 回调（模拟一分钟），仍然 limited。`sample()` 一旦 limited 就提前返回，resize / orientation 也不会重建这个对象。
- `renderCost` 在每个回调清零，但只在实际绘制后写入；60Hz 回调、30Hz 绘制、每次绘制 9ms，按回调平均只得到约 4.5ms，不触发 `>5ms`。这不是每次绘制的平均成本。
- `renderer.render()` 的 JavaScript 耗时不是 GPU 完成耗时。缺少 GPU 计时，不能把这个值当成 GPU budget。
- 大于 250ms 的回调间隔全部跳过。持续 300ms 间隔、100ms 成本的极端反例反而不降级。该保护用于排除挂起有价值，但缺少持续严重过载的另一条判断路径。
- 星空仍按 `frame += 1` 和流星 `life -= 1` 推进，限帧后动画速度 / 生命周期跟着改变；月球自转使用 delta，但惯性和插值系数仍按绘制次数应用。稳定节奏与时间推进应分开修正。

候选 deadline 调度只在重放中验证了平均绘制次数，不保证每帧等间距，也不代表 GPU 性能提升。例如 75Hz 屏幕上的 30Hz 仍会有不同长度的间隔。修复应保留余量、每个回调最多绘制一次、挂起后重置时间基准，避免补画一串过期帧；最终目标应由真实设备验证，不能把继续锁在 30/20Hz 视为完成优化。

## 3. 宽屏渲染的候选初始瓶颈

### 大面积 CSS 混合 / 滤镜

`stage.css:21` 的两层雾图 `inset:-25%`，每层未变换面积为视口的 2.25 倍；`stage.css:124` 的极光 `inset:-18%`，为 1.8496 倍；`base.css:391` 的 grain `inset:-10%`，为 1.44 倍。它们不受 Canvas 的 800k / 1.05M 预算控制。`screen` / `overlay`、透明度、旋转缩放和滤镜可能要求额外中间表面或混合工作，是否逐帧栅格化必须由 trace 判断。

几何量级示例：**假设** CSS 视口 3840×2160、DPR 1，每层雾图未变换面积约 18.66M 设备像素，极光 15.34M，grain 11.94M；星空 backing store 则仅 1192×670，约 0.799M。CSS 2194×1234、DPR 1.75 的设备像素量级也接近上述数字。这不是本机 CSS 视口实测，不是显存占用或实际 raster tile 分配；裁剪、缓存、缩放和旋转都会改变实际开销。

**横竖方向本身不足以解释这里的所有差异**：1440×900 与 900×1440 在相同 DPR 下上述面积相同。必须比较同像素面积、同鼠标/触摸能力的横竖屏，同时记录 CSS 布局断点和月球尺寸。不能拿隐藏了雾图等效果的触屏竖屏与保留所有效果的桌面宽屏，直接推导“横屏尺寸是唯一根因”。

`.stage` 已是 fixed 且有 z-index 的堆叠上下文，雾层 / 极光也已有 `will-change:transform`。不能预设再加一次 `will-change` 或 `isolation` 就能解决，必须检查实际 render pass、重绘区域和缓存行为。

### SVG 动画

`stage.css:73` 的三条全视口 SVG 路径持续动画 `stroke-dashoffset`。它们可能每帧触发绘制 / 栅格化，而不是只做 transform 合成；是否导致大范围 invalidation 未验证。这个候选应独立于雾图和 grain 隔离，不能把所有 CSS / SVG 同时关闭后统一归因于混合模式。

### 画布、毛玻璃及 GSAP

- 星空每次生成多个全画布渐变和逐星路径；已存在像素预算不代表 CPU 绘制与上传成本已排除。它在宽屏滚动时暂停，对首屏静置反馈帮助有限。
- 月球 antialias、透明画布和高性能偏好仍需对照。实际 GPU、WebGL GPU 用时及跨 GPU 复制成本未取得，无法评价 RTX / 核显路由。
- 导航毛玻璃在 `data-scrolled=true` 时启用，初始页顶导航没有该规则的 blur；菜单也有 blur。若页顶关闭菜单时已卡顿，它的优先级低于持续全屏效果。滚动停在页中后的静置仍需要测它。
- GSAP 有入场和滚动 scrub；静置反馈使“仅滚动处理造成卡顿”的解释不完整，不能排除持续 ticker 或别的脚本。Cursor 静止后还会每个 rAF 更新 transform，但其实际成本也未测量，优先做停稳后停止写入的低风险对照。

## 5. 下一轮现场对照协议

先记录：页面执行的资源 URL / 哈希、CSS `innerWidth/innerHeight`、DPR、`visualViewport.scale`、Chrome 页面缩放百分比、`screen.width/height`、显示器物理分辨率和刷新率、主题、motion、hover/pointer、系统电源状态。DPR 同时受系统缩放与页面缩放影响，`visualViewport.scale=1` 也不能单独证明 Chrome 页面缩放 100%。

在同一个日常 Chrome / 同一显示器 / 同一电源状态下，先测自然视口，再测桌面鼠标能力的 1440×900 与 900×1440（等面积），补测 844×390 与 390×844（等面积且能力一致）。触屏模拟作为另一组，不与桌面对照混用。每个视口须完整重载，因为月球 compact / 贴图和初始星星数量有挂载时判断。所有分组 warm-up、初始滚动位置和数据偏好一致，记录实际 backing store 及 limited 的触发时间。

每条件至少三轮，穿插基线，例如 A-B-A / B-A-B；每次从新加载的正常预算状态起跑，避免上一次的永久 limited 污染下一次结果。预热至少 8 秒，独立记录：页顶静置 10 秒、滚动过程 10 秒（相同视口/秒的速度并覆盖同一区域）、页中停稳静置 10 秒；交互另测。

每项实验只改一个因素，全部恢复后再进入下一项：

| 单因素对照 | 操作含义 | 必须避免的误读 |
| --- | --- | --- |
| 星空 | 冻结绘制，保留最后一帧和布局 | `display:none` 不会停止其 JS 循环，不是 CPU 隔离 |
| 月球 | 停止该 renderer 提交，保留最后一帧 | 只隐藏 DOM 可能仍保留 render 成本；离屏 observer 也会改变行为 |
| 雾图 | 分别冻结变换、隐藏单层、仅取消 blend、仅取消固定 filter | 冻结后仍可能因为背后 Canvas 更新而继续混合；每个子项独立重载 |
| 极光 | 与雾图分开，冻结 / blend 对照 | 不与雾图一起关闭后直接命名主因 |
| grain | 独立冻结、独立去 blend、独立隐藏 | 保留底下场景运动，检查混合带宽与全屏 invalidation |
| 毛玻璃 | 页中同位置只取消 backdrop-filter | 同时记录导航和菜单是否启用，避免对本来没有 blur 的页顶下结论 |
| SVG | 仅暂停三条 flow 的 dashoffset，其他 CSS 动画保留 | 检查 Paint / Raster 是否下降；环线与其他 SVG 动画需分别补测 |

可先用暂停与正常状态的单变量实验定位，再仅对命中的因素实施局部候选修复。禁止先全关效果后推导唯一根因。

记录 Performance 主线程（JS / style / layout / paint）、Raster、Compositor / Viz / GPU 轨迹与 render pass / layer 边界，以及 Frame rendering stats / Frames 的成功、部分呈现和丢弃帧。rAF 间隔、Canvas draw 次数、WebGL draw call 次数、实际呈现帧必须分别命名；月球一次 render 含多个 draw call，不能直接把 drawElements 次数当成帧数。Long Task 为零也不能排除 20–40ms 的持续过载或 GPU 瓶颈。

日常 Chrome 的合成 GPU 与页面 WebGL GPU 要分别取证。只记录 browser GPU info / `chrome://gpu` / 可授权的 WebGL renderer 诊断，不改变 GPU 偏好或驱动设置。若跨 GPU 拷贝没有轨迹证据，只记为候选。GPU timer 不可用时明确空缺，不用同步 `gl.finish()` 阻塞测量。

只有单因素对照在三轮中方向一致、相关 trace 开销同时下降，并在恢复 A 时回归，才提升其根因置信度。候选优化还需同场景 GPU 复测、深浅主题截图差分及人工视觉验收；帧数恢复不能替代视觉验收。

Chrome 对 Frames / GPU raster 的解释：[Frame rendering stats](https://developer.chrome.com/docs/devtools/rendering/performance)。rAF 的回调语义和基于时间推进动画的要求：[MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。

### 已实施的代码变化

- `RenderClock` 默认不设应用层上限，每个活动 rAF 都允许绘制；可选档位仅为 60、45。限帧保留下一次截止时间的余量，每个回调最多绘制一次，避免 30.5Hz → 15.25 次/秒的跳帧放大；暂停后清空时间债务。
- `RenderBudget` 在实际 draw 完成后接收 CPU 毫秒数，与回调观察分开。慢回调、隐藏、离屏或滚动暂停本身不再被当成这个画布的绘制超载。
- 2 秒预热后，以 2 秒窗口观察自身 CPU 占用；连续两个窗口超过 65% 才依次进入 60、45 档。按每次真实绘制的平均 CPU 耗时投影下一档占用，连续六个窗口低于 45% 后依次恢复 60、无上限。两个阈值及窗口是保守的初始策略参数，**没有真实 GPU 数据支持其为设备最优值**。
- 恢复 / 升档的投影基于 rAF 回调节奏估计，不把它当作显示器刷新率或实际呈现 FPS。它是每个画布自身 CPU 的后备保护，**没有检测或证明 GPU / 合成瓶颈**，也不统筹两个画布与 CSS 的总负载。
- 像素预算与帧率解耦。保留原有正常上限：星空 800,000px，月球 1,048,576px；移除因 limited 自动降低到 450,000 / 589,824px 的路径。没有增加新的清晰度牺牲，既有正常档的上采样仍然存在。
- 星空位移、流星生命周期、指针缓动及月球惯性 / 插值按经过时间推进，以原正常 30Hz 动态速率为基准，避免高刷新率导致运动加快。月球原有按时间计算的自转保留。
- 可见性、画布尺寸改变、主题 / motion 切换会重置过期预算和时钟。保留已有宽屏滚动期间星空暂停、离屏月球暂停和 calm / reduced-motion 静态行为；“无上限”指活动动态绘制时的调度，不表示取消这些暂停。
- 为后续获准的诊断提供非视觉属性：星空 `.stage__canvas`、月球 `.moon__canvas` 的 `data-render-fps` 为 `native`、`60` 或 `45`，仅在状态改变时写入。
- CSS、图片、贴图、材质、混合层和视觉布局未修改；没有把 CSS / SVG 假设作为已确认根因实施视觉改造。
